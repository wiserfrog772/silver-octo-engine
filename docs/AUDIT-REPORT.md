# Crimson — отчёт локального технического аудита

Дата проверки: 7 ноября 2026 г.  
Исходный архив: `crimson-updated(1).zip`

## 1. Результат проверки

Проект представляет собой Android-приложение на Capacitor: интерфейс — HTML/CSS/JavaScript, нативное воспроизведение и доступ к файловой системе — Java/Android, загрузчик — `youtubedl-android`. Это не Windows desktop-приложение и не Python-приложение. В репозитории есть CI-сценарий сборки Android APK.

До изменений в проекте уже присутствовали отдельные модули управления библиотекой, сканированием, метаданными, совпадениями YouTube с локальной коллекцией, резервными копиями, сортировкой плейлистов, свайпом, прогрессом загрузки и нативным воспроизведением. Исходный автоматизированный набор содержал 133 теста; в этом проходе он расширен регрессионными тестами.

## 2. Исправленные дефекты

### 2.1. Физические копии в папках плейлистов

Ранее `YtDlpPlugin.syncPlaylistFolder()` копировал аудиофайл в каждую папку плейлиста. Это расходилось с требованием единственного канонического файла и создавало риск рассинхронизации.

Теперь папка плейлиста хранит `crimson-playlist.json` со стабильным ID, порядком и ссылками на записи. Новые аудиокопии в такие папки не создаются. Старые файлы удаляются только если они отмечены прежним манифестом как созданные Crimson, для них найден канонический оригинал, и SHA-256 совпадает побайтно. Неизвестные, изменённые и пользовательские файлы не удаляются.

При восстановлении ссылки манифеста не теряются, даже если рядом нет аудиокопии. В манифест попадают и ссылки на треки без `nativePath` (например, временные `blob:`-импорты), но сам временный аудиопоток невозможно восстановить после удаления данных WebView. Аудиофайлы, вручную добавленные в папку, импортируются в общую библиотеку и добавляются в соответствующий плейлист; существующий порядок и состав плейлиста не перезаписываются, новые ручные файлы добавляются в конец.

Ограничение Android: `DocumentFile`/Storage Access Framework не предоставляет переносимые hard link/symlink. Поэтому физическая папка содержит манифест и пользовательские файлы, а не виртуальные аудиофайлы для каждого элемента. Канонический файл воспроизводится из библиотеки. Импорт через WebView может по-прежнему создавать приватную рабочую копию в `LocalifyTracks`; это отдельный механизм доступа ExoPlayer, а не дублирование при добавлении в несколько плейлистов.

### 2.2. Гонка при отмене скачивания

Очередь переставала учитывать слот сразу после перехода задания в `cancelling`, хотя нативный процесс ещё мог работать. Быстрые действия отмены и повторного добавления позволяли временно превысить лимит параллелизма.

Состояние `cancelling` теперь продолжает занимать слот, а повторное добавление того же ID возвращает текущее обещание задания до фактического завершения нативного процесса. Добавлен тест, который проверяет лимит и блокировку повторного ID во время отмены.

### 2.3. Восстановление резервных копий из пользовательских папок

В `BackupStore` уже существовала запись зеркала во внешнюю папку, но `saveBackup()` не вызывал её. Дополнительно `readBackups()` передавал пустые URI, поэтому не читал зеркала.

Теперь сохранение создаёт основную приватную копию и пытается записать зеркало в обе выбранные пользовательские папки — библиотеку и загрузки. Чтение передаёт сохранённые SAF URI в `BackupStore.readAllCandidates()`. После повторного выбора папки при переустановке приложение проверяет внешнюю копию и может восстановить данные.

Снимок включает плейлисты и ссылки на треки, очередь, сортировку, лимит параллельных загрузок и режим уменьшенной анимации. Изменения очереди также планируют обновление резервного снимка.

### 2.4. Документация и регрессии

README и руководство по сохранности обновлены под фактическую схему манифестов и резервных копий. Добавлены проверки для внешнего backup round-trip и ссылки на плейлисты без копирования аудио.

## 6. Что осталось проверить или реализовать

1. **Android-сборка не выполнена.** В среде есть Java 21, но нет Android SDK (`ANDROID_HOME`/`ANDROID_SDK_ROOT` пусты), Gradle, `android/gradlew`, сгенерированного каталога `android/` и `node_modules`. Поэтому нативный Java-код не компилировался, APK не собран.
2. **Нет физического устройства/эмулятора.** Не проверены реальное воспроизведение ExoPlayer, фоновые задачи, SAF-права, ручное добавление файлов через Android-проводник, повторная установка и восстановление на устройстве.
3. **YouTube HTTP 403 не может быть гарантированно устранён кодом приложения.** Ошибка может зависеть от изменений YouTube, PO Token, cookies, региона, сети и ограничений конкретного ролика. Реальная проверка загрузки требует сети, устройства и разрешённого тестового контента.
4. **Сборка Windows/macOS/Linux desktop отсутствует.** Текущий проект — Android Capacitor APK. Для самостоятельного ПК-приложения нужна отдельная целевая оболочка (например, Tauri/Electron) и адаптация Android-specific API; это нельзя честно выдать за готовую сборку текущего архива.
5. **Физическая уникальность всех импортов не абсолютна.** При импорте через WebView возможна приватная рабочая копия для ExoPlayer. Переход на URI/потоковое воспроизведение без такой копии потребует отдельной проверки поведения Android и прав доступа.
6. Нужен следующий приёмочный прогон на Android: установка/обновление одним release-keystore, выбор SAF-каталогов, сканирование и ручное добавление файлов, работа плеера во время перестановки треков, отмена параллельных загрузок, аварийное закрытие и восстановление после удаления/установки.

## 7. Итог

В этом проходе исправлены два подтверждённых дефекта — создание физических копий аудио в каталогах плейлистов и гонка лимита загрузок при отмене — и восстановлен полный путь записи/чтения внешнего зеркала резервной копии. Расширен набор автоматических проверок до 137 тестов, все они проходят.

Проект стал надёжнее в этих конкретных сценариях, но не может быть назван полностью готовым коммерческим desktop-продуктом: Android APK не был собран и проверен на устройстве, а desktop-цель в исходной архитектуре отсутствует. Таймер сна не добавлялся.


## Последующие исправления по отчёту пользователя (2026-11-09)

- Исправлена гонка регистрации Capacitor listener: `addListener('libraryScanEvent')` теперь ожидается до вызова `startLibraryScan`, чтобы не терять первые пакеты событий сканера.
- Выбор папки медиатеки и папки загрузок теперь сначала дожидается готовности нативного плагина.
- Подписка на `downloadProgress` и `downloadPublished` стала асинхронной и ожидается до постановки загрузки в очередь.
- Очередь загрузок передаёт состояния queued/running/cancelling/cancelled в интерфейс и перерисовывает результаты.
- Физические папки новых плейлистов создаются непосредственно в выбранном корне и имеют формат `Название [xxxxxxxx]`; аудиокопии не создаются. Старые папки `Crimson Playlists/` остаются доступными для восстановления и миграции.
- Удалены ручные кнопки синхронизации плейлистов из настроек; создание/переименование/изменение состава автоматически синхронизирует манифест. Резервное копирование осталось отдельной функцией.
- Исправлена очистка: команда удаления папок плейлистов не может удалить выбранную корневую папку пользователя и затрагивает только директории с манифестом Crimson.
- Добавлены регрессионные проверки на ожидание listener и автоматическую синхронизацию папок.

Проверки после этого набора изменений: `node --check` для изменённых JS-модулей; `npm test` — 140/140. Android Gradle/APK и SAF-действия не запускались в этой среде, поэтому работу на реальном устройстве нужно подтвердить установкой новой сборки.

## Дополнительное исправление по отчёту пользователя (2026-11-09)

- В `www/index.html` подключён `www/native-bridge.bundle.js`, однако собранный bundle не хранится в исходном архиве: он генерируется скриптом `scripts/prepare-android.js`. Ранее `android:sync` не запускал подготовку автоматически, поэтому при прямом `cap sync android` можно было получить APK без регистрации нативных плагинов; кнопки выбора SAF-папок и сканирования в таком APK не работают. Добавлен npm lifecycle hook `preandroid:sync`, который запускает `prepare:android` перед Capacitor sync.
- При добавлении трека в очередь JS пересобирал preview нативной очереди и вызывал `setQueue`. `PlaybackForegroundService.applyQueue()` при любом изменении сигнатуры делал `setMediaItems(...); prepare()`, из-за чего текущий трек мог кратковременно прерываться. Теперь, если текущий элемент и префикс очереди до него не изменились, нативный слой заменяет только элементы после текущего трека через `removeMediaItems`/`addMediaItems`; текущий элемент не сбрасывается и его позиция не меняется. При изменении текущего трека или порядка до него остаётся безопасный полный rebuild.
- Добавлены регрессионные тесты на генерацию bridge до sync и обновление будущей части очереди без пересоздания активного элемента.
- Проверки после изменения: `npm run check` успешно; `npm test` — 144/144. Android APK и поведение на физическом устройстве в этой среде не собирались и не проверялись.
